# pstack 与 Codex–Claude 的连接方式

pstack v0.15.43 由 Lauren Tan 编写，原始方法、工作流、脚本和 [MIT 许可](../../pstack/LICENSE) 在同级 `pstack/` 目录逐文件保留。先从 [pstack 完整索引](pstack-index.md) 按任务选择原版子技能。流程和原则以 [原版 poteto-mode](../../pstack/skills/poteto-mode/SKILL.md) 及所选子技能为准。本页只描述如何把原版工作接到我们的协作环境。

## 工作区规则

`cc-all-in-one` 的 `AGENTS.md` 指向本机已安装的技能，并点名这些事：代理角色映射、反向合并 `dev`、人工提测、提交前格式化、真实 Console 验收和登录交接。做法在本页后面几节和 [Mini 主流程](../SKILL.md)。

并行代理用 `~/.codex/agents/` 里的 `pstack-*.toml`。没有这些文件时，按 [cc-setup](../skills/cc-setup/SKILL.md#codex-代理) 配置。换机器时核对 `~/.codex/config.toml` 里的技能路径是否仍指向这次安装。

| 当原版流程需要 | 在我们的环境中怎样做 |
| --- | --- |
| 实现前理解入口、定位根因或评估影响 | Codex 收集复现、正常对照和相关代码。涉及协议、类型转换或跨层改动时，先找仓库里最接近的实现，核对输入、输出和职责。调用契约可以保持时，沿用现有入口，把行为差异放到负责该语义的一层。CloudCanal 测试命令经 Mini 测试入口执行 |
| 指定执行者或独立评审 | 按用户指定分工。Claude 可以负责实现或评审，Codex 可以独立复核。需要把问题交给 Claude 时，使用[英文交接和共享会话](claude-collaboration.md) |
| 以真实入口验证改动 | 先确定要观察的结果。CloudCanal 功能在单测和组件测试之外，按 [Mini 主流程](../SKILL.md) 完成浏览器页面验收及所需的部署与版本核对，其他仓库沿用自己的工具和环境 |
| 把一个成熟流程重跑或扩大规模 | 复用原版验证、独立评审和交付指南。环境准备、数据源和交付授权沿用用户当前仓库的约束 |

验证 Binlog 等协议兼容性时，先用同一份真实协议样本对照 `dev` 和当前版本，记录最早失败的环节。使用测试夹具时，分别注明列定义和实际协议编码。夹具与真实数据有差异时，将结论限定在夹具实际覆盖的环节。

共享终端正忙时，Codex 可以继续读代码、准备数据和独立跑测试。验证结果分开记录为源码核对、单测、构建和实库读回。选择原版流程时只加载需要的子技能。

## 反向合并 dev

| 规则 | 检查方式 |
| --- | --- |
| 反向合并覆盖 `cc-all-in-one` 下所有独立 Git 项目。逐仓库获取 `origin/dev`，核对当前分支和工作区。功能分支合入 `origin/dev`，本地 `dev` 用快进同步。 | 完成后运行 `python3 ~/.codex/skills/cloudcanal-dev-test/scripts/check_dev_merges.py`。脚本自动发现项目，直接查询各自远端 `dev`，逐仓库核对其提交已包含在当前 `HEAD`。检查失败时，按仓库报告缺失提交、冲突或其他阻塞。 |

## 编码约定

传给方法或构造器的值需要解析、转换或组合时，先用有业务含义的局部变量命名结果。Java 新增或修改的局部变量使用实际类型，例如先写 `ZoneId sourceTimestampZone = ObDsUtil.toLogProxyZoneId(config.getSrcTimeZone());`，再传入 `sourceTimestampZone`。评审本轮新增的 Java 代码时，检查局部变量声明是否仍有 `var`。

## 更新人工提测文档

新建时复制 [CloudCanal 内部提测模板](qa-template.md)。填入标题中的版本、分支和开发人，按本轮范围列出「开发自测」的三级标题。标题确定后保留一份底稿，用于对照校验。

| 规则 | 检查方式 |
| --- | --- |
| 用户提供原稿或模板时，在该稿上修改。沿用标题、章节、顺序和列表格式，在原有章节里补用例和验收条件。 | 编辑前保留一份原稿。交付前运行 `python3 ~/.codex/skills/cloudcanal-dev-test/scripts/check_qa_template.py <原稿或已定标题的底稿.md> <交付文档.md>`，核对开头和标题。另逐项核对列表、表格和链接。 |
| 「需求」「修复」里新增的功能支持条目以「支持」开头。例如「支持 TiDB 源端和目标端配置 JDBC 连接时区」。 | 同一命令会提示新写或改写的条目行号。第一份文件只有模板标题时，加 `--original <修改前的提测稿.md>`，以原稿判断哪些条目是新写的。 |
| 「开发自测」先写结论。保留任务配置、作业 ID 和待测项，删掉重复操作过程。 | 逐项检查结果和证据。交付可直接导入语雀的 Markdown。 |

## 提交前格式化

提交前列出本次提交涉及的全部 Java 文件，包括新增、修改和重命名后的文件。使用 IntelliJ IDEA 的 **Reformat Code** 对这些文件执行整文件格式化。`cc-all-in-one` 使用项目配置的 `canal-format`。同一文件含有其他任务的改动时，先隔离本次提交的内容。格式化后重新检查差异和暂存范围，再提交。

需要在 IDEA 按数据库或改动目的归类时，用 `pika-idea-control` 确认 Changelist 的文件和归属。

| 规则 | 检查方式 |
| --- | --- |
| 本次提交涉及的每个 Java 文件都检查整份文件。日志英文正文的首字母用大写，含原有日志和标签后的正文。 | 暂存后在仓库根目录运行 `python3 ~/.codex/skills/cloudcanal-dev-test/scripts/check_java_log_initials.py`。按报告的文件和行号修正，再暂存并重跑。 |
| 用 `//` 拆开的 Java 调用，每个参数末尾都写 `//`，包括最后一个。`);` 单独占下一行。 | 在仓库根目录运行 `python3 ~/.codex/skills/cloudcanal-dev-test/scripts/check_java_call_wrap.py`。脚本只检查本次 diff 中新出现的这种调用。 |
| 新增或改签名的 Java 方法、构造器中，每个自定义参数都应有实际用途。 | 暂存后在仓库根目录用 JDK 17 或更高版本运行 `java ~/.codex/skills/cloudcanal-dev-test/scripts/CheckJavaParameters.java`。沿调用点追到最终读取该值的业务操作。若整条链没有消费者，从声明和调用方一并删除该参数。 |

日志首字母和 Java 参数检查默认读取暂存区，复核已有提交时加 `--commit <提交>`。本轮 Java 改动可以直接把文件路径传给日志检查，对工作区整份文件做检查。`//` 调用检查读取 `HEAD` 到工作区的差异和未跟踪的 Java 文件。参数检查支持 `--between <旧提交> <新提交>`，也可在 `--` 后附仓库相对路径，限定检查范围。

参数检查用 JDK 语法树比较两个版本中具名类型的成员声明，报告方法体中从未作为标识符出现的参数。注释、字符串和 `this.ddl` 均不会算作使用参数 `ddl`。单纯转发、赋值或嵌套作用域里的同名引用都可能通过，仍需人工追踪。检查跳过无方法体的声明、局部类和匿名类的方法、record 构造器和标准 `main(String[])` 入口。为保留继承契约，也跳过标记为 `@Override` 的方法、单参数 `equals`，以及显式声明父类型的类或接口中可能覆盖父方法的实例方法。

## Codex 工具对应关系

- 原版提到 Cursor `Task` 或特定模型时，按 [cc-setup](../skills/cc-setup/SKILL.md#codex-代理) 分派。把代码复核、数据准备、日志分析等可独立验收的工作并行分派，席位空出后补派已就绪的独立任务。需要独立评审但缺少独立执行者时，在验收记录写明实际完成的检查。
- 原版提到 `/loop` 来等待当前任务时，用当前 Codex 会话继续检查，直到出现完成条件或具体阻塞。
- 原版的外部会话、插件安装、自动化、推送、开 PR 和合并步骤沿用用户在具体任务中授予的权限。

本轮的一个实际组合是由 Codex 在测试环境发现字节校验误报，Claude 实现最小补丁，Codex 再独立复跑。验收同时包含相同字节能通过、`80FF` 与 `0080FF` 能检出，以及实际写入和校验分开核实。
